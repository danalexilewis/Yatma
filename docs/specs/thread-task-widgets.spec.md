# Acceptance model

> These scenarios describe target behavior, not implemented or verified behavior.
> The implementation plan and facade definitions are in
> [thread-task-widgets.md](../plans/thread-task-widgets.md).
>
> The WTW-01 through WTW-26 identifiers are scenario families. Former table cases
> are explicit scenarios with numbered suffixes; WTW-22 separates partial,
> resolved, and durable streaming states. Facade/task annotations are comments,
> not Gurki keywords or Cucumber tags. Relative time belongs in authored steps;
> fixed clocks and timezone dates belong in the implementation test fixtures.
>
> Unless stated otherwise, the workspace is ready and uses one signed-in account.
> A rendered copy is a widget inside the current render window. Each scenario is
> an independent possible path; Outputs across alternatives are not deployment
> counts. Derived reports are generated by Gurki, not a second authored source.

System: Yatma thread task widgets

Scenario: WTW-01 Completing one of five copies updates every rendered copy
Given an open task appears in five separate replies
When I check the task in the first reply and the local save commits
Then all five copies show the task as completed
And the shared task detail shows the task as completed
And only one task status change is saved
Output 1 committed task-status change and 5 completed widget presentations
Outcome the person can act on any occurrence without reconciling copies manually
Activates WTW-02 Reopening a different copy persists across reload
# Facades: F1; Tasks: W2

Scenario: WTW-02 Reopening a different copy persists across reload
Given a completed task appears in five separate replies
When I uncheck the task in the fourth reply and the local save commits
And I reload the workspace
Then every loaded copy shows the task as open
And opening another old reply shows the task as open
And no Undo-reason dialog is requested for this status edit
Output 1 committed reopening and the reloaded open widget presentations
Outcome the reopened task remains actionable through old and new conversation views
# Facades: F1; Tasks: W2

Scenario: WTW-03 Repeated occurrences inside one reply remain independently rendered
Given one reply references the same task twice with different commentary
When the reply is displayed and I complete one occurrence
Then both occurrences remain visible in their original positions
And each occurrence retains its own commentary
And both checkboxes show the committed completion
Output 2 distinct rendered occurrences backed by 1 task identity
Outcome both contextual mentions remain usable without conflicting task state
# Facades: F1, F2; Tasks: W1, W2

Scenario: WTW-04 Checking a task does not rewrite an earlier task selection

Outcome the person retains the original reading context while task state changes
